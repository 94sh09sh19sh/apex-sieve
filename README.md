# Apex Sieve（全域登頂篩）使用說明

> **先窮盡，後登頂。**
> 不是直接想選項，而是先圈出整片可能的空間，剔除不能的，再在剩下的空間裡找最高點。

Apex Sieve 是一個全域 Claude Code skill，把「先找最大可行集合、再排序找最優」的選擇流程整理成 12 個步驟（0～11）。適合任何「要從一大片可能中挑出幾個」的決策：比賽選題、專題選題、研究主題、技術選型、產品方向等。

名字的由來：**Sieve**（篩子）代表前半段的窮盡與剔除，**Apex**（頂點）代表後半段在可行空間裡找最高點。

## 1. 快速開始

在任何專案目錄下的 Claude Code 中輸入：

```
/apex-sieve 我要從所有可能的個人專案裡選 3 個來做，條件寫在 docs/需求.md
```

或直接用自然語言描述，例如「幫我從所有可能的畢業專題題目中選一個，不要漏掉選項」，Claude 也會自動啟用這個 skill。

接下來的互動只有兩輪：

1. **Claude 送出開場問卷**（已依情境預填能推定的部分）→ 你回答或修改
2. **Claude 送出對齊稿**（把你的回答補充詳盡、標出它補的東西）→ 你回覆「核准」

核准後 Claude 會一路做到底，中途不再問你（除非遇到「阻斷條件」，見第 4 節最後）。最後你會拿到一份完整的決策報告檔。

> 小技巧：先把需求文件、比賽規則、先前的討論都放進專案目錄或貼進對話，Claude 預填得越多，你要回答的就越少。素材足夠時，Claude 會直接把問卷和對齊稿合併成一輪。

## 2. 整體流程

```
階段 A：開場對齊（你決定）           階段 B：執行（AI 完成）
┌──────────────────────────┐        ┌──────────────────────────────────┐
│ 0  定出宇集 U              │        │ 2  切軸：多條低相關的軸交叉出格子  │
│ 1  評分條件與加權方式       │  核准  │ 3  套用限制：交叉一致性剔除        │
│ 3  硬限制與軟限制          │ ────→ │ 4  剔除前先試救回                  │
│ 7  最後要幾個（k）          │        │ 5  對可行空間均勻取樣              │
│                            │        │ 6  評分                            │
│ 一次問完 → 對齊稿 → 核准    │        │ 7  對前 3k 名做敏感度分析          │
└──────────────────────────┘        │ 8  組合與合併                      │
                                      │ 9  承諾前先驗證關鍵假設            │
                                      │ 10 決策紀錄（你一人拍板）          │
                                      │ 11 停損條件與回頭檢查建議          │
                                      └──────────────────────────────────┘
```

| 步驟 | 誰決定 | 做什麼 | 防的是什麼 |
|---|---|---|---|
| 0 | 你 | 定義一個「選項」是什麼、範圍在哪、目標是什麼 | 宇集本身不完整 |
| 1 | 你 | 評分條件、錨點、加權方式 | 權重和真實偏好不一致、重複計分 |
| 2 | AI | 參考領域專業分類，切出 2～4 條均勻且低相關的軸 | 只用一條軸切，看不到跨類別的組合 |
| 3 | 你＋AI 補 | 硬限制剔除，軟限制留到評分 | 把「不想選」誤當成「不能選」 |
| 4 | AI | 剔除前先試改造救回 | 誤殺 |
| 5 | AI | 每個可行格子都產生具體選項，並做覆蓋檢查 | 評分時又回到憑印象舉例 |
| 6 | AI | 依錨點評分，沒把握的給區間 | 假的精確度 |
| 7 | 你定 k，AI 做分析 | 對前 3k 名做權重與分數擾動 | 名次其實不可靠 |
| 8 | AI | 寫出組合條件、合併互補的選項、選出 k 個 | 前 k 名不等於最佳組合 |
| 9 | AI | 驗證最關鍵的假設 | 承諾後才發現前提錯了 |
| 10 | 你 | 看一頁決策紀錄後拍板 | — |
| 11 | AI | 停損條件、回頭檢查索引 | 規則改了卻沒回頭檢查 |

## 3. 開場：你需要決定的四件事

開場問卷一次問完，以下是每一題在問什麼、為什麼要問。

### 步驟 0｜宇集 U

| 題目 | 說明 | 例子 |
|---|---|---|
| 0-1 選的單位 | 一個「選項」是什麼 | 一款遊戲；一個題目 |
| 0-2 層級 | 選到多細 | 遊戲「類型」或「具體一款」 |
| 0-3 邊界 | 哪些一開始就不考慮 | 不考慮需要付費授權的方案 |
| 0-4 目標 | 最終要達成什麼 | 評審分數最高；同時練到新技術 |
| 0-5 已想到的候選 | 可留空，只用來檢查覆蓋率 | 記帳小幫手、讀書計時器 |

**對齊時 Claude 會做的事**：寫出 U 的正式定義、舉出在範圍內與不在範圍內的邊界例子、檢查你的選項是否混了不同層級（例如機制、題材、形式混在一起）、把混在一起的兩個目標（外部評分＋自己的偏好）拆開。

### 步驟 1｜評分條件與加權方式

| 題目 | 選項 |
|---|---|
| 1-1 評分條件 | 每條一句話定義 |
| 1-2 偏好結構 | A 可互補／B 嚴格順位（字典序）／C 混合（門檻＋加權） |
| 1-3 加權方式 | 直接給權重／名次加總（rank-sum）／名次重心（ROC）／擺盪權重／等權重 |
| 1-4 分數尺度 | 預設 1–5 分 |
| 1-5 評分者 | AI 單一評分（預設）／AI 多視角獨立評分／你親自複評前 3k 名 |

**對齊時 Claude 會做的事**：
- 為每條條件寫出 1／3／5 分的**錨點**
- 算出實際權重數字，名次法會同時列出 rank-sum 和 ROC 讓你比較
- **一致性檢查**：你說「使用者價值是主軸，其他是副產品」，卻選了 4:3:2:1 加權？Claude 會指出這兩種說法互相矛盾，請你擇一
- **重複計分檢查**：「使用者人數」和「市場潛力」是不是在量同一件事
- **致命傷檢查**：某條拿最低分是否代表根本做不成？若是，建議改成門檻
- 定出平手門檻 δ（預設 0.1 分）

### 步驟 3｜硬限制與軟限制

| 類型 | 意義 | 請附上 |
|---|---|---|
| 硬限制 | 違反就出局 | 來源（法規、物理、競賽規則、委託方要求、資源上限） |
| 軟限制 | 不喜歡但可以權衡 | 可以接受的程度（門檻） |

**對齊時 Claude 會做的事**：
- **降級**：你自己推論而來的要求（例如「一定要用最新的框架」）不能當硬限制，會改成軟限制加門檻，或搬回評分條件
- **程度問題**：「規則太複雜」改成具體門檻
- **錯放**：「和別的選項重複」不是可行性問題，移到步驟 8
- **補齊缺漏**：依情境補上你沒提到的限制（時間、預算、技能、平台、法規、使用族群條件等），標為〔AI 補〕讓你核准或刪除

判斷口訣：**違反它，是「做不到」還是「不想選」？「做不到」才是硬限制。**

### 步驟 7｜最後要幾個

| 題目 | 說明 |
|---|---|
| 7-1 數量 k | 最後要幾個；敏感度分析會做前 3k 名 |
| 7-2 關係 | 各自獨立，還是要一起搭配 |
| 7-3 組合條件 | 可留空，Claude 會擬草稿（例：每個目的至少一款主力、總成本上限） |

### 核准之後

對齊稿核准後會寫進報告檔第一節，標記為**凍結規格**。之後如果你想改任何一條，請用回頭檢查模式（第 6 節），Claude 會只重跑受影響的部分，並留下變更紀錄。

## 4. 執行：AI 自動完成的步驟

每完成一個步驟，Claude 會在對話中用 2～4 行回報重點，細節都寫進報告檔。

### 步驟 2｜切軸

- 先查這個領域的專業分類方式（例：遊戲設計的 MDA 架構、產品設計的待完成任務），在報告中寫明出處
- 決定 2～4 條軸，每條軸 3～7 個值，同一條軸只有一種層級
- **均勻**：各軸的值數量與粒度相近
- **低相關**：兩兩檢查，若某軸的值幾乎決定另一軸的值，就合併或換軸
- 另外定一條**反向檢查軸**，不參與交叉，只在步驟 5 檢查有沒有漏掉的區塊

### 步驟 3、4｜剔除與救援

- 先做**值對相容性**檢查（例：「無螢幕」×「圖像辨識」一次剔除所有相關格子），再做格子層級檢查
- 軟限制不在這裡剔除
- 剔除前先寫出這個選項的**核心價值**，再試改造：拿掉子功能、換元件、縮小範圍、改形式、換情境
- 改造後仍保有核心價值 → 救回；失去核心價值 → 照樣剔除
- 每一筆都記入**剔除追溯表**，這是之後回頭檢查的索引

### 步驟 5｜均勻取樣

- 每個可行格子至少產生 1 個具體選項
- 格子太多時用分層取樣，確保每條軸的每個值出現次數大致相等，並附覆蓋表
- 你在 0-5 給的既有候選這時才拿出來比對：如果某個既有候選落在被剔除的格子，Claude 會回頭確認剔除理由
- 用反向檢查軸找空白區塊，漏掉的就補

### 步驟 6｜評分

- 依錨點評分，每格附一句理由
- 沒把握的分數給區間 `[下限, 最可能, 上限]`
- 套用軟限制門檻（剔除前同樣先試救回）
- 兩個目標分開算、分開列

### 步驟 7｜敏感度分析

對前 3k 名執行 `scripts/sensitivity.js`，看：
- 單一權重 ±20% 時前 k 名會不會變
- 權重放大或縮小到幾倍時前 k 名開始改變（**翻轉點**）
- 換成等權重、rank-sum、ROC、名次倒數時結果會不會變
- 蒙地卡羅模擬（權重與分數同時擾動 2000 次）下，每個選項進入前 k 名的機率

依入選率分成**穩定入選**（≥ 80%）、**邊緣**（30%～80%）、**偶爾**（< 30%）。邊緣選項之間的取捨不硬靠分數，改看互補性、風險、驗證成本。

### 步驟 8｜組合與合併

- 先寫出組合條件，再選
- 檢查能不能把互補的選項合併成更強的混合選項（合併後重新檢查限制與評分）
- 每個入選選項標明**角色**（骨幹、補位）和**備案**

### 步驟 9｜驗證關鍵假設

- 列出每個入選選項依賴的假設，依「影響 × 不確定性」排序
- Claude 能驗證的（查文件、上網查證、讀程式碼、找實例）直接驗證並附證據
- 不能驗證的，寫出最便宜的檢驗方式、通過標準與期限
- 假設被推翻時，局部重做受影響的步驟

### 步驟 10｜決策紀錄

決策者預設是你一人，不做共識流程。Claude 產出一頁決策紀錄：最終選項、主要理由、放棄了什麼、備案、仍待驗證的假設。

### 步驟 11｜停損與回頭檢查

- 每個選項的**停損條件**：指標、門檻、檢查時間點、觸發後換成哪個備案
- **回頭檢查索引**：限制 → 被它剔除的選項；評分條件 → 對它敏感的選項；假設 → 依賴它的選項
- **觸發規則**：發生什麼事要重跑哪些步驟

### 阻斷條件（執行中唯一會再問你的情況）

- 所有格子都被硬限制剔除，或可行選項少於 k
- 兩條硬限制互相矛盾
- 驗證發現凍結規格的前提是錯的（例：比賽規則和你描述的不同）
- 你選了「親自複評前 3k 名」，需要你交回評分

其他情況 Claude 一律自行判斷，並寫進報告的「AI 判斷紀錄」，你事後可以逐條檢查。

## 6. 回頭檢查模式

規則改了、假設被推翻、停損條件被觸發時使用：

```
/apex-sieve 回頭檢查 apex-sieve_個人專案_20261010.md 預算從 0 元放寬到每月 300 元
```

Claude 會讀取報告中的凍結規格與回頭檢查索引，只重跑受影響的部分：

| 變更 | 重跑 |
|---|---|
| 限制放寬或刪除 | 把當初被它剔除的格子與選項拉回來，從步驟 4 重走，再進入步驟 5～8 |
| 限制收緊或新增 | 檢查現有選項是否違反，違反的先救援，再重做步驟 8 |
| 權重或評分條件改變 | 重做步驟 6（只改受影響的條件）與步驟 7、8 |
| 假設被推翻或停損被觸發 | 換成備案，或重做步驟 8，並更新步驟 9～11 |

每次回頭檢查都會在報告末尾的「變更紀錄」新增一筆，凍結規格的版本號也會更新。

## 7. 敏感度分析腳本

`scripts/sensitivity.js` 只用 Node 內建模組，不需安裝套件。也可以單獨使用：

```
node ~/.claude/skills/apex-sieve/scripts/sensitivity.js 輸入.json --out 結果.md
```

輸入格式（完整說明見 `references/sensitivity-input.md`）：

```json
{
  "k": 3,
  "criteria": [
    { "id": "C1", "name": "使用者價值", "weight": 4, "rank": 1 },
    { "id": "C2", "name": "可行性", "weight": 3, "rank": 2 }
  ],
  "candidates": [
    { "id": "P1", "name": "記帳小幫手", "scores": { "C1": 5, "C2": 3 } },
    { "id": "P3", "name": "讀書計時器", "scores": { "C1": [3, 4, 4], "C2": 3 } }
  ],
  "options": { "mode": "weighted", "runs": 2000, "seed": 42 }
}
```

- 分數寫單一數字＝有把握；寫 `[下限, 最可能, 上限]`＝不確定，模擬時會在區間內抽樣
- `rank` 全部填上時，會額外比較 rank-sum、ROC、名次倒數
- `mode` 設為 `lexicographic` 時改用字典序，只擾動分數
- 固定 `seed` 可讓結果重現

## 8. 常見問題

**Q：一定要回答所有問題嗎？**
不用。標了〔AI 預填〕的同意就不用改；留空的題目 Claude 會在對齊稿中提出建議，你核准即可。只有 k（要選幾個）和評分條件，最好由你明確給出。

**Q：為什麼要「一次問完」，不能邊做邊問？**
邊做邊問容易讓後面的結果影響前面的標準（看到某個選項排很前面，就回頭調權重讓它更前面）。先凍結規格再執行，結果才可信。真的要改，就走回頭檢查，並留下紀錄。

**Q：步驟 2 的軸我可以指定嗎？**
可以。在開場時直接告訴 Claude 你想用的軸，它會照用，但仍會做均勻與低相關的檢查，有問題會在對齊稿中提出。

**Q：決策者不只我一人怎麼辦？**
這個 skill 預設單一決策者。如果還有其他人會影響最終決定，建議在開場前先和他們一起定好步驟 1 的評分條件與權重，再把結果交給 Claude，這樣流程的結論比較不會在最後被推翻。

**Q：可行選項很少，還需要走完全部步驟嗎？**
需要，但會很快。步驟 2 切軸和步驟 5 的反向檢查，正是用來確認「選項少」是因為真的少，而不是因為漏想。

**Q：k = 1 時，「前 3k 名」只有 3 個，夠嗎？**
夠。敏感度分析的目的是確認第 1 名是否穩定，前 3 名足以看出它和第 2、3 名的差距是否可靠。若第 3 名有平手，會一起納入。

**Q：評分都是 AI 給的，可信嗎？**
三個機制降低風險：錨點事先定義並經你核准；沒把握的分數用區間表示，並在敏感度分析中擾動；決定結果的關鍵分數會在步驟 9 列為待驗證假設。若你想多一層保險，開場時在 1-5 選「AI 多視角獨立評分」或「親自複評」。

**Q：會不會跑很久？**
規模主要取決於格子數和選項數。對齊稿最後會附上預估規模（幾條軸、約多少格、約多少個選項），你可以在核准前要求縮小。

## 10. 設計依據

這個 skill 從一套實際用過的選擇流程出發，補齊理論上缺少的步驟而成：

| 原本的做法 | 補上的步驟 | 在 skill 中的位置 |
|---|---|---|
| 用「全集減去不可行」定義集合 | 用多條低相關的軸切出全集，加上反向檢查軸 | 步驟 2、5 |
| 剔除規則沒分外部硬限制和自己加的要求 | 每條限制標來源，自己推論的要求降為軟限制 | 步驟 3 對齊 |
| 權重和自己陳述的偏好結構不一致 | 一致性檢查、重複計分檢查、致命傷改門檻 | 步驟 1 對齊 |
| 評分時又回到舉例產生選項 | 依格子均勻取樣並附覆蓋表 | 步驟 5 |
| 敏感度分析只做前五名，或沒做 | 固定對前 3k 名做，並有可重現的腳本 | 步驟 7 |
| 組合規則停留在判斷，沒寫出來 | 先寫組合條件再選，每個選項有角色與備案 | 步驟 8 |
| 規則改變時沒有回頭檢查 | 剔除追溯表、回頭檢查索引、回頭檢查模式 | 步驟 4、11、回頭檢查模式 |

| 承諾前先驗證假設 ✓ | 保留，並依「影響 × 不確定性」排序 | 步驟 9 |
